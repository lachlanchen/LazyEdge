# LazyEdge v0.3.0

v0.3.0 makes LazyEdge transport-only. Browser UI, sign-in, sessions, chat
history, attachment storage and PWA cache/version control now belong to an
independently released application rather than the transport package.

## What changed

- Removed the v0.2 private-chat BFF, browser assets, session store, service
  worker and `lazyedge-chat.service` renderer.
- Added explicit `exposure: public|private` service intent and bounded
  `spec.edge.privateListeners` for authenticated edge-local callers.
- Enforced strict role-specific bindings: the edge cannot receive an upstream
  authorization file and the worker cannot receive a client-token store.
- Kept public hostname, method and path policy default-deny and kept private
  listeners out of Caddy, certificate and NAT artifacts.
- Added bounded cleanup and recovery tests for streams, incomplete uploads,
  unavailable tunnels and multiple private listeners.

## Breaking upgrade boundary

A v0.2 `lazyedge-chat.service` cannot run through a launcher that will move to
v0.3 because the `serve chat` command no longer exists. Before changing a
launcher, either pin that exact legacy unit to a retained immutable v0.2
artifact or retire it after its replacement application has independently
passed sign-in, session, streaming, image-input, update and rollback tests.

Both edge and worker must be staged from the same exact v0.3.0 tarball. Render
their units with immutable executable paths, validate the role-specific
bindings, and retain independently runnable prior edge and worker artifacts.
Do not call a tag, npm publication, symlink update or successful tunnel a
deployment. Follow the complete [v0.2 to v0.3 upgrade
guide](../upgrading-v0.2-to-v0.3.md).

## Publication and deployment identity

The repository metadata names v0.3.0, but the authoritative published version
is the npm registry record and its exact integrity/checksum. The authoritative
deployed version is the executable path and process identity verified on each
host. These identities can advance independently and must be recorded
separately.

## Authoritative publication path

The upstream v0.3.0 release uses exactly one publication path: commit and tag
the reviewed bytes, publish a stable GitHub Release for that tag, and let
`.github/workflows/publish.yml` publish to npm through trusted OIDC with
provenance. Manual workflow dispatch is validation-only. Do not run
`release:npm` or `publish:npm:current` for this upstream release and do not
switch to direct local publication if OIDC fails. Preserve the same commit,
tag, and version, repair the trust mapping, and retry the trusted workflow.
